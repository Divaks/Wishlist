# Wishlist API

## Локальний запуск

Потрібні PostgreSQL 16 та Node.js 24 LTS. Скопіюйте кореневий `.env.example` у `.env`, задайте пароль БД і встановіть `JWT_SECRET` зі значення `openssl rand -hex 32`. Запустіть `docker compose up -d postgres`. У `couple-wishlist-api/` виконайте `npm ci`, `npm run build` і `npm run start:prod`. Змінні процесу мають пріоритет над файлами середовища.

## Перехід із main

Перед оновленням збережіть резервну копію та явно задайте `DB_NAME` поточної БД. Запустіть один екземпляр API для застосування транзакційної міграції, потім решту. Для відкату відновіть резервну копію разом із попередньою версією застосунку. Якщо наявні email збігаються після приведення до нижнього регістру, міграція зупиниться. Визначте власників конфліктних записів до повторного запуску.

Міграція зберігає старі бажання та бронювання і створює групу для кожної взаємної партнерської пари. Клієнти можуть далі звертатися до бажань за старими числовими ID. Нові відповіді містять UUID. Для історичних бажань без часу створення порядок визначається перенесеним ID.

| Попередній клієнт | Перехід |
|---|---|
| Масиви з GET /wishlist, /groups, /groups/:id/wishes | Ці маршрути й далі повертають масиви. Для пагінації додайте /paged і query-параметри page та limit. Відповідь містить data, total, page, limit і totalPages. |
| POST /users/generate-code і POST /users/connect | Власник запрошує за email через POST /groups/:id/members. Адресат переглядає GET /groups/invitations і приймає через POST /groups/:id/invitations/accept. Оновіть клієнти партнерських маршрутів до розгортання. |
| GET /wishlist/partner | Отримайте групу з GET /groups і відкрийте GET /groups/:id/wishes/:memberId. Цей маршрут підтримує пагінацію. |
| Видалення бажання | DELETE /wishlist/:id повертає 204. |
| Видалення акаунта | Власник групи спочатку передає права або видаляє групу. Інакше API повертає 409. |
| Профіль | PATCH /users/profile приймає календарну дату YYYY-MM-DD або null для очищення. GET /users/profile читає актуальні поля облікового запису. |

Під час бронювання лише один конкурентний запит отримує 201. Решта отримують 409. Власник бажання не бачить броні. Інші учасники бачать стан, а особу того, хто забронював, API показує лише йому самому.

## Перевірки

У каталозі API виконайте `npm run lint`, `npm test -- --runInBand --coverage`, `npm run build` і `npm run test:e2e -- --runInBand`. Для E2E задайте змінні підключення PostgreSQL у середовищі процесу. Використовуйте тестовий сервер і роль із правом CREATEDB. Набір створює й видаляє окрему БД з випадковим ім’ям.

### Перевірка живого API

Використовуйте окрему локальну або тестову БД. Smoke-тест створює три випадкові акаунти, групу та бажання й намагається видалити ці дані навіть після помилки. Для локальної перевірки виберіть окрему назву БД у `.env` перед першим запуском PostgreSQL. Якщо контейнер використовує вже ініціалізований том, створіть окрему БД вручну або використайте окремий тестовий екземпляр PostgreSQL.

У першому терміналі від кореня репозиторію:

```bash
docker compose up -d postgres
cd couple-wishlist-api
npm ci
npm run build
npm run start:prod
```

У другому терміналі від кореня репозиторію:

```bash
curl --fail http://127.0.0.1:3000/health
cd couple-wishlist-api
npm run test:smoke
```

Встановіть `API_URL=http://127.0.0.1:3001` перед `npm run test:smoke`, якщо API слухає порт 3001. Скрипт `couple-wishlist-api/__tests__/test-api.ts` перевіряє всі 29 HTTP-маршрутів за функціональними сценаріями. Він також перевіряє помилковий пароль, валідацію, доступ до групи до прийняття запрошення й після видалення учасника, видимість бронювання та видалення записів.

Для ручної перевірки зареєструйте тестовий акаунт через `POST /auth/register` з JSON-полями `email`, `password` і необов’язковим `name`. Надішліть ті самі `email` і `password` у `POST /auth/login`. Використайте отриманий `accessToken` у заголовку `Authorization: Bearer <accessToken>` для запитів `GET /users/profile`, `GET /groups` та `GET /wishlist`.
